When an enclave forgets: rollback-resistant registers and the TEE-Rex recovery protocol

October 18, 2026
Tags: distributed-systems trusted execution fault tolerance replication crash recovery

Trusted execution environments (TEEs) such as Intel SGX and ARM TrustZone suggest a shortcut for building fault-tolerant systems. If a replica’s code runs inside a hardware enclave, the replica cannot be made to lie, so a protocol that only tolerates crashes should be enough, and crash tolerance is far cheaper than tolerating arbitrary (Byzantine) behavior. The paper by Sadegh Keshavarzi, Gregory Chockler and Alexey Gotsman, published at DISC 2025, examines a gap in that reasoning. An enclave protects a program while it runs. Once the machine powers off, the state the program saved to disk sits outside that protection, and on restart an attacker can hand the program an older but perfectly authentic copy of it. This is a rollback attack.

The authors ask what it costs to build the most basic replicated object, a read/write register, when replicas can crash, restart and roll back. A register is simply a stored value that clients can read and overwrite; a replicated register keeps copies of that value on several machines, called replicas, so that it survives some of them failing. The authors define a failure model for this setting, prove tight bounds on the number of replicas required under fixed failure thresholds and under a more flexible model that limits how often failures happen, and present TEE-Rex, a register protocol whose recovery procedure rebuilds a restarted replica’s state from its peers, using neither durable storage (a disk or other storage that survives a restart) nor hardware monotonic counters (explained below). Along the way they report safety bugs in two earlier recoverable register protocols.

What a TEE is, and why enclave code is trusted not to lie

A trusted execution environment is a feature of the processor that lets a program run part of its code, and keep part of its data, inside a protected region called an enclave. Intel SGX (Software Guard Extensions) is the TEE offered on Intel processors, and ARM TrustZone is the corresponding feature on ARM processors. The paper names both only as examples and does not depend on the details of either. What it relies on is the guarantee they share: while the program runs, the code and the state placed in the enclave are shielded by the hardware, so an attacker with access to the machine cannot change what the enclave code does or edit the data it holds.

Not all data fits in an enclave, so programs also keep state outside it, in ordinary memory or on disk. To protect that state, the program keeps integrity metadata inside the enclave and checks the outside data against it. A common form is a Merkle tree: a tree of hashes whose root summarizes all the data, so that changing any piece of the data changes the root. With the root kept in the enclave, any alteration of the outside data while the program runs is detected.

This is what “cannot be made to lie” means. A replica can fail in two broad ways. It can stop or go quiet: it crashes, or some of its messages are lost, which is called an omission failure. Or it can behave arbitrarily: send wrong values, tell different peers different things, or ignore the protocol altogether. Failures of the second kind are called Byzantine, and tolerating them needs more replicas, more messages and more round trips. If the protocol code runs in an enclave and its data is either inside the enclave or checked against metadata kept there, an attacker cannot make the replica send anything the protocol would not send. What the attacker can still do is switch the machine off, crash the program, or drop and delay its messages. Earlier systems used exactly this argument to turn Byzantine failures into crash or omission failures. The paper accepts the premise for a running enclave: in its model every replica, faulty or not, executes the prescribed code, and attacks on the TEE itself are not modeled. Its point is that the premise breaks at restart, as the next section explains.

Sealing proves authorship, not freshness

The paper starts from the cost of Byzantine fault tolerance. Tolerating replicas that behave arbitrarily is expensive in message complexity (the number of messages exchanged), in latency, and in the number of replicas: the classic register bound is n≥3k+1n \ge 3k + 1n≥3k+1 replicas to tolerate kkk Byzantine ones. As described above, a TEE lets a system replace Byzantine failures with crash or omission failures, which are cheaper to tolerate.

The protection lasts only while the program executes. For persistent state, which must be kept in non-volatile storage such as a disk or flash so that it survives power-off, hardware vendors provide sealing: the program encrypts state with a device-specific key before writing it out. On restart, the TEE can check that the sealed blob was produced by itself at some point. It cannot check that the blob is the latest one it produced. An attacker who keeps old copies can substitute one undetectably.

The standard fix is a persistent monotonic counter in hardware: a counter that can only increase and that survives restarts. Binding it to the sealed state lets the program recognize a stale copy, because the copy carries an older counter value. The paper notes that such counters are implemented on flash memory, which gives poor write performance and quick wear-out, that they are not supported by every TEE vendor, and that Intel SGX has deprecated its monotonic counter service. Distributed alternatives exist, in which a group of machines jointly maintains the counter, such as ROTE and Engraft, and the paper argues later that they give up liveness. The question the paper sets out to answer is what can be built with no trusted persistent state at all.

Crash-restart-rollback: one failure model for TEE replicas

The system is asynchronous and message-passing: processes communicate only by sending messages, and there is no bound on how long a message takes to arrive or how fast a process runs. There are n>1n > 1n>1 replicas that store the register’s state and an unbounded set of clients that issue reads and writes. Clients can only crash permanently. To study the role of disks, s≥0s \ge 0s≥0 of the replicas have access to non-volatile storage. Handling a received message is atomic with respect to storage: its effects on non-volatile storage are persisted entirely or not at all.

Replicas follow the crash-restart-rollback model, abbreviated CRR. A replica may crash permanently, or it may restart, in which case it runs an on-restart block, a piece of recovery code executed first after the restart, and then continues. A crash and the restart that follows it are modeled as a single atomic event. A restarted replica that has finished its on-restart block is called active. On restart, a replica with non-volatile storage may also suffer a rollback, meaning its storage reverts to a version older than the one it held before the crash.

The model sorts replicas into four disjoint classes. A perfect replica never crashes. A benign replica crashes and restarts at least once, is eventually up for good (from some point on it never crashes again), and never rolls back. A crash-faulty replica crashes without restarting, or crashes and restarts infinitely often, and never rolls back. A rollback-faulty replica rolls back at least once. Perfect and benign replicas are correct; the other two classes are faulty. CRR extends the classical crash-recovery model, in which processes may crash and come back but their disks are never rolled back, by adding rollbacks, and it is strictly weaker than the Byzantine model because every replica, even a faulty one, runs the prescribed code.

The channel assumption is deliberately weak. Messages between two processes are guaranteed to arrive only if both are up from some time onward and the message is sent after that time. A message sent to a replica that later crashes may simply vanish, which forces protocols to retransmit.

Correctness is split into safety, meaning nothing bad ever happens (for example, a read never returns a wrong value), and liveness, meaning something good eventually happens (for example, every operation eventually finishes). For safety the paper uses atomicity, also called linearizability (defined by Herlihy and Wing): every read and write appears to take effect at a single instant between its start and its end, so the replicated register behaves like one copy accessed one operation at a time. The weaker safeness (defined by Lamport) only requires that a read that does not overlap any write return the last value written. For liveness it uses wait-freedom (defined by Herlihy): every operation of a client that does not crash finishes, whatever other clients do; and the weaker obstruction-freedom, which only guarantees that an operation finishes if it eventually runs without interference from other operations. Registers can be single-writer/single-reader (SWSR) or multi-writer/multi-reader (MWMR). An implementation is tolerant of a failure model if it is both safe and live in every execution the model allows. The static model CRR(k,r,b)\mathrm{CRR}(k, r, b)CRR(k,r,b) caps, in every execution, the number of faulty replicas at kkk, rollback-faulty replicas at r≤kr \le kr≤k, and benign replicas at bbb.

Why fewer replicas cannot work

The lower bound is a partition argument: it splits the replicas into groups and builds two executions that each look correct on their own but cannot both be handled correctly once they are combined. Suppose n=2k+gn = 2k + gn=2k+g with g≤min⁡(b,r)g \le \min(b, r)g≤min(b,r). Split the replicas into F1F_1F1​ and F2F_2F2​, each of size kkk, and GGG, of size ggg.

In a first execution, the replicas in F1F_1F1​ are silent, as if crashed, and a write of vvv completes using only F2F_2F2​ and GGG. Obstruction-freedom forces it to finish because at most kkk replicas are faulty. In a second execution, F2F_2F2​ is silent, the replicas of GGG crash and restart (so they are benign, which is allowed because g≤bg \le bg≤b), and a read completes using F1F_1F1​ and GGG. No write ever happened, so the read must return the initial value.

Now glue the two together: run the first execution, then let GGG crash, restart and roll back to its initial state, then run the second. Rollback makes GGG look exactly as it did at the start of the second execution, and F1F_1F1​ never received anything. The read returns the initial value even though the write completed earlier, which violates safety. The glued execution has at most g≤rg \le rg≤r rollback-faulty replicas, so it is allowed. The two constraints g≤bg \le bg≤b and g≤rg \le rg≤r are why the bound uses min⁡(b,r)\min(b, r)min(b,r).

The storage bound follows the same pattern. If fewer than 2k+r+12k + r + 12k+r+1 replicas have disks, place as many disk-equipped replicas as possible in F1∪F2F_1 \cup F_2F1​∪F2​. Then GGG contains at most rrr of them, which can roll back, while the diskless members of GGG lose their memory on restart anyway.

Algorithm A: one ABD skeleton, two quorum rules

The upper bound comes from algorithm A, a variant of the MWMR version of ABD, the classical quorum-based register by Attiya, Bar-Noy and Dolev. A quorum is a subset of replicas that an operation must hear from before it can finish; quorum sizes are chosen so that every read quorum overlaps every write quorum in enough replicas for a read to see the latest completed write. Each replica stores a value and a timestamp, where a timestamp is a pair of a counter and a client identifier ordered lexicographically: first by counter, with ties broken by client identifier. Each replica also keeps a Boolean stale flag; a stale replica does not answer read requests.

Clients use two helper functions. One, read_quorum, sends a READ request to all replicas and waits for replies from qrq_rqr​ of them. The other, write_quorum, sends a WRITE request and waits for qwq_wqw​ acknowledgments. Both retransmit until they hear enough replies, because of the weak channels. A replica that receives a write with a higher timestamp than its own adopts the new value and timestamp, and acknowledges either way.

A write first reads timestamps from a read quorum, picks the highest counter, and writes the value with timestamp (counter + 1, own id) to a write quorum. A read collects timestamp-value pairs from a read quorum, picks the pair with the highest timestamp, writes it back to a write quorum, and returns its value. A message delay is the time one message takes to travel, so a request and its reply cost two. Each operation is two such round trips, hence 4 message delays.

The algorithm evaluates the predicate P(n,k,r,b)=(2k+r+1≤n<2k+b+1)P(n, k, r, b) = (2k + r + 1 \le n < 2k + b + 1)P(n,k,r,b)=(2k+r+1≤n<2k+b+1) to choose its quorum sizes, its restart behavior and whether to use disks. Figure 1 shows the choice.

Both variants rest on one key property.

Property 3 (Real-Time Order). If a call to write_quorum that writes timestamp xxx completes, and a call to read_quorum starts after that, then the read returns a set containing a timestamp ≥x\ge x≥x.

For A1, the write reached n−kn - kn−k replicas and the read heard from n−kn - kn−k replicas, so the two sets share at least (n−k)+(n−k)−n=n−2k(n - k) + (n - k) - n = n - 2k(n−k)+(n−k)−n=n−2k replicas. Since 2k+r+12k + r + 12k+r+1 replicas persist their state, at least (n−2k)+(2k+r+1)−n=r+1(n - 2k) + (2k + r + 1) - n = r + 1(n−2k)+(2k+r+1)−n=r+1 replicas in that intersection have disks. At most rrr replicas ever roll back, so at least one replica in the intersection both persists its state and never rolls back. Timestamps only grow during normal execution, so that replica reports a timestamp ≥x\ge x≥x. The paper’s proof text says at one point that the read quorum has k+1k + 1k+1 replicas, but the intersection it computes uses n−kn - kn−k, the size the pseudocode assigns to A1. A1 is wait-free because at least n−kn - kn−k replicas are eventually up, so both quorums are eventually available, and restarted replicas can still answer reads because their stale flag stays false.

For A2, any read quorum of k+1k + 1k+1 and write quorum of n−kn - kn−k share at least one replica. A replica in a read quorum cannot have crashed since the write, because any restart sets the stale flag and stale replicas do not answer reads. Without crashes, timestamps never decrease, so the shared replica reports a timestamp ≥x\ge x≥x. This argument does not depend on the thresholds, so A2 is safe in every execution, even when n<2k+r+1n < 2k + r + 1n<2k+r+1. It is wait-free when n≥2k+b+1n \ge 2k + b + 1n≥2k+b+1: at least n−(k+b)≥k+1n - (k + b) \ge k + 1n−(k+b)≥k+1 replicas never crash, so a read quorum of non-stale replicas always exists, and at least n−kn - kn−k replicas are eventually up, so a write quorum eventually exists.

From Property 3 the paper derives linearizability with a dependency-graph technique in the style of Adya’s work. Each operation gets the timestamp it read or wrote, and edges between operations are defined from those timestamps: real-time order (one operation finished before the other started), read-from (a read returned the value of a write), write-write (one write’s timestamp is lower than another’s), and anti-dependency (a read saw a value that a later write overwrote). The proof shows the graph has no cycles, so the operations can be laid out in one sequential order that respects all edges, which is a valid linearization.

Dynamic failures: trading thresholds for limited churn

Static thresholds are a strong assumption for long-lived systems: over time, every replica may restart and possibly roll back. By Theorem 1, no protocol can be both safe and live in all executions below the static bound, so the authors weaken the liveness requirement instead.

They assume a constant Δ\DeltaΔ such that a message sent at time ttt arrives by t+Δt + \Deltat+Δ if both endpoints stay up during [t,t+Δ][t, t + \Delta][t,t+Δ]. Because there is no lower bound on message delays or processing times, processes cannot measure the passage of time, and the model stays asynchronous in the sense that matters for algorithm design.

Definition 4. An execution is CRR-D(d,c,M)\mathrm{CRR\text{-}D}(d, c, M)CRR-D(d,c,M)-valid if there is a set UUU of at least n−dn - dn−d replicas that are all eventually up, and either (1) c>dc > dc>d and any two crash events are more than MΔM\DeltaMΔ apart, or (2) some subset S⊆US \subseteq US⊆U of at least n−cn - cn−c replicas never crashes.

The parameter ddd bounds the replicas that are not eventually up, and implementations must know it. The two conditions say that either failures are spaced out, as in the churn assumptions used for dynamic systems (churn being the rate at which machines leave and rejoin), or at most c≥dc \ge dc≥d replicas crash at all. MMM depends on the implementation and represents how long a replica needs to recover before the next crash. Neither condition restricts how many replicas roll back.

Why a restarted replica cannot just ask around

TEE-Rex reuses the read and write procedures of algorithm A, with read quorums of d+1d + 1d+1 and write quorums of n−dn - dn−d, mirroring A2’s k+1k + 1k+1 and n−kn - kn−k. Like A2 it relies on the stale flag. A2 alone is not enough, though. Consider an execution in which every replica eventually stays up but each crashes and restarts once, with consecutive crashes MΔM\DeltaMΔ apart. It is CRR-D(0,n,M)\mathrm{CRR\text{-}D}(0, n, M)CRR-D(0,n,M)-valid, yet A2 eventually runs out of non-stale replicas and reads block forever. Restarted replicas need a way to rebuild their state and clear the stale flag.

The obvious recovery, querying a read quorum and adopting the freshest state, breaks linearizability. The paper’s Example 9 uses n=3n = 3n=3, d=1d = 1d=1, c=1c = 1c=1, so quorums are of size 2; Figure 2 shows it.

The write collected acknowledgments from p3p_3p3​ and p2p_2p2​, but p3p_3p3​’s acknowledgment was invalidated by its own restart, which it repaired using p2p_2p2​’s state from before p2p_2p2​ saw the write.

The repair, following Michael et al. (2017), is to require that the acknowledgments a write collects be crash-consistent. Definition 10 states it precisely: a set EEE of WRITE_ACK events is crash-consistent if, whenever a replica that sent an acknowledgment in EEE later crashes, restarts and queries a read quorum for its state, none of the READ_ACK replies it gets was sent by a replica before that replica sent its own acknowledgment in EEE. In Figure 2, p2p_2p2​ answered p3p_3p3​’s recovery read before acknowledging the write, so the set of acknowledgments is not crash-consistent.

Detecting stale acknowledgments with incarnation numbers and crash vectors

Each TEE-Rex replica keeps an incarnation number, initially 0 and increased by each recovery, so that it identifies which life of the replica sent a message. It also keeps a crash vector, an array with one entry per replica holding the highest incarnation number it knows for that replica. The replica’s own incarnation number is stored in its own entry of the crash vector. The authors first assume the incarnation numbers a replica assigns are strictly increasing and positive (Property 11, Incarnation Number Monotonicity), which a never-rolled-back hardware counter would provide, and remove the assumption later.

For a register write, a replica piggybacks (attaches) its incarnation number and its whole crash vector on each WRITE_ACK. The writer loops. It sends WRITE to every replica not yet validated, waits until validated plus newly acknowledging replicas reach n−dn - dn−d, takes the entry-wise maximum of all received crash vectors, and discards any acknowledgment whose incarnation number is below the maximum entry for its sender. A lower number means that the sender restarted while the write was still gathering replies. A writer always trusts its own acknowledgment. If the surviving set is still a write quorum, the write returns; otherwise the loop repeats.

Recovery runs as follows in this basic version. The restarted replica sets stale, picks a new incarnation number, writes it to a write quorum, then reads full states, including crash vectors, from a read quorum. Its READ requests carry the new incarnation number, and each responder records it in its crash vector. Finally the replica merges the crash vectors it received, adopts the value with the highest timestamp, and clears stale.

The paper’s Example 12 replays Figure 2 under this scheme. p3p_3p3​ acknowledged the write with incarnation g1g_1g1​, then recovered with g2>g1g_2 > g_1g2​>g1​ and sent g2g_2g2​ to p2p_2p2​ in its state request. p2p_2p2​ recorded g2g_2g2​ and later piggybacked that crash vector on its acknowledgment to p4p_4p4​. p4p_4p4​ then sees that p3p_3p3​’s acknowledgment carries g1<g2g_1 < g_2g1​<g2​, discards it, and keeps waiting, so the bad execution is ruled out.

The new incarnation number is written in two places, and each serves a purpose. The write to a write quorum, done crash-consistently, lets other replicas reconstruct this replica’s incarnation number when they themselves restart; if p2p_2p2​ crashed between answering p3p_3p3​ and answering p4p_4p4​, its own recovery read would still bring back g2g_2g2​. The write piggybacked on the state read reaches the specific read quorum used for recovery, which intersects every write quorum a concurrent register write might use, so such a write can detect that the recovery compromised its acknowledgments.

Writing incarnation numbers while peers are still recovering

Writing incarnation numbers with the same mechanism as register values, as Michael et al. did, can deadlock, meaning that replicas wait for each other forever. The paper’s Example 13 uses n=5n = 5n=5, d=1d = 1d=1, c=3c = 3c=3: p1p_1p1​ crashes for good, p2p_2p2​ and p3p_3p3​ restart once at the start, p4p_4p4​ and p5p_5p5​ never crash. The execution satisfies condition 2 of Definition 4. Both recovering replicas need n−d=4n - d = 4n−d=4 acknowledgments for their incarnation write, but only active replicas answer, and there are only two.

TEE-Rex therefore lets a replica accept writes to crash vectors even while its stale flag is set. Such a replica may not have rebuilt its crash vector yet, so it returns a placeholder ⊥\bot⊥ instead. The writer then validates incarnation writes differently: after collecting enough acknowledgments, it explicitly reads crash vectors from a read quorum, and only active replicas, which hold valid crash vectors, answer that read. In Example 13, p2p_2p2​ and p3p_3p3​ gather acknowledgments from p2,p3,p4,p5p_2, p_3, p_4, p_5p2​,p3​,p4​,p5​ and read crash vectors from p4p_4p4​ and p5p_5p5​.

Monotonic incarnation numbers without a hardware counter

Without trusted storage, a replica cannot remember its last incarnation number, and simply reading it back from a quorum fails: if the replica crashed before its incarnation write completed, the read may not return its latest number, which breaks Property 11.

TEE-Rex uses two phases. Each replica keeps a second vector, the pre-crash-vector. Before adopting a new incarnation number, the replica writes it crash-consistently into the pre-vector entry for itself at a write quorum. On restart, it reads that entry from a read quorum, takes the maximum, and adds one. Because the write quorum used for the pre-vector intersects the read quorum used on the next restart, each new incarnation number exceeds every number the replica previously adopted. Figure 3 shows the complete recovery sequence.

One subtlety remains. A replica must answer pre-vector writes while it is still restarting, to avoid the Example 13 deadlock, but at that point it does not yet know its own incarnation number, so it is unclear what to put in its acknowledgment. TEE-Rex lets the writer piggyback, on each WRITE it sends to a replica, the highest incarnation number it knows for that replica; the receiver adopts that number and echoes it. Replicas may temporarily carry stale incarnation numbers this way, but the paper proves that Property 11 still holds.

The paper’s Example 15 shows this at work with n=5n = 5n=5, d=1d = 1d=1, c=3c = 3c=3. After one round of restarts, p4p_4p4​ and p5p_5p5​ record incarnation 1 for p2p_2p2​ and p3p_3p3​. Both restart again, find their previous number 1, and try to store 2 in their pre-vector entries. p2p_2p2​’s first WRITE to p3p_3p3​ carries 0, which p3p_3p3​ echoes; reading crash vectors from p4p_4p4​ and p5p_5p5​ shows 1 for p3p_3p3​, so the acknowledgment is discarded, and symmetrically at p3p_3p3​. Each then sends 1, the other echoes it, and p2p_2p2​ validates and completes its recovery with incarnation 2. When p3p_3p3​ next reads crash vectors it sees 2 for p2p_2p2​, discards p2p_2p2​’s older acknowledgment, retries with 2, validates, and finishes with incarnation 2 as well.

How the proofs go

Safety centers on durable writes: a completed quorum write is durable if every replica in its validated set, whenever it is active after acknowledging, holds a value at least as large as the one written. A durable write is seen by every later read (Lemma 29). The authors show by a minimal-counterexample argument (assume some write is not durable, take the earliest such write, and derive a contradiction) that all incarnation-number writes are durable, then that every register write’s acknowledgments are crash-consistent and the write is durable, which gives Property 3. The linearizability proof of algorithm A then carries over. For the full algorithm, durability of the pre-vector writes yields Incarnation Number Monotonicity.

Liveness rests on timing under the spacing condition. The authors define M^\hat{M}M^ as 6 for the basic algorithm and 12 for the enhanced one, the number of message delays a restart needs. With crashes more than M^Δ\hat{M}\DeltaM^Δ apart and at most one replica up but not active, each read_quorum by the restarting replica completes within 2Δ2\Delta2Δ and each incarnation write within 4Δ4\Delta4Δ. The basic restart is a write followed by a read, 6Δ6\Delta6Δ; the enhanced restart is read, write, write, read, 12Δ12\Delta12Δ. From this they show that at most one replica is ever up but not active, so at least n−cn - cn−c replicas are always active, enough for a read quorum of d+1d + 1d+1. Every eventually-up replica eventually becomes active (Corollary 55), so a write quorum of n−dn - dn−d active replicas eventually exists, and client operations complete.

Where earlier recoverable registers go wrong

The related-work section, backed by appendices, reports concrete counterexamples. Guerraoui et al. (2008) studied registers when only some processes have durable storage. In their protocol, a restarted diskless replica regards itself as up to date once it accepts a single WRITE. The authors construct an execution with n=2a+3b+1n = 2a + 3b + 1n=2a+3b+1 replicas, write quorums of a+2b+1a + 2b + 1a+2b+1 and read quorums of a+b+1a + b + 1a+b+1, in which a recovered replica receives a delayed message from an older write and then answers a read with the older value, so the read misses a newer completed write. The faulty assumption is that whoever sends a write has recently read the latest value, which asynchrony breaks. They give a correct alternative for that model: A1-style quorums of n−fn - fn−f when s>2fs > 2fs>2f, and A2-style quorums with write quorums of n−fn - fn−f and read quorums of uuu when u>fu > fu>f, where uuu counts always-up processes.

Dinis et al. (2023) proposed the rollback-recovery (RR) model for TEE replication. RR excludes permanent crashes, so it is weaker than CRR, and its register uses ordinary write quorums without crash-consistency checks. With MR=F=2M_R = F = 2MR​=F=2, giving 5 replicas, write quorums of 3 and read quorums of 3+min⁡(s,2)3 + \min(s, 2)3+min(s,2), where sss counts suspicious repliers, the authors exhibit a violation of the same shape as Figure 2: a replica acknowledges a write, rolls back, refreshes from three replicas that have not seen the write, and the write completes while a quorum unaware of it remains. The paper also notes that reads in that design are not wait-free.

Paxos and viewstamped replication are consensus protocols that keep the replicas of a service applying the same commands in the same order, an approach called state machine replication. Practical variants of them by Chandra et al., Kończak et al., and Liskov and Cowling assumed crash recovery without durable storage but did not use crash-consistent quorums, and Michael et al. showed they can violate safety. Jehl et al. and Michael et al. use versioning similar to crash vectors but depend on replicas tracking their incarnations across restarts, which in TEEs requires hardware counters. The technical report of Michael et al. suggests a distributed mechanism without a full implementation, and their register’s liveness under static failures requires n=2c+1n = 2c + 1n=2c+1. ROTE writes a counter to a write quorum and reads it back from the same quorum; the authors argue this is safe but not live, since the same quorum need not be available twice in a row, and that Engraft inherits the issue.

What the analysis establishes: tight replica counts and crash-level latency, with no experiments

The paper is entirely analytical. It contains no implementation, no hardware testbed, no workload and no measurements. Its results are impossibility proofs, algorithms given as pseudocode, and correctness proofs for those algorithms, with latency counted in message delays and recovery time in multiples of Δ\DeltaΔ.

The headline results are replica counts. Table 2 collects the bounds the paper states or cites.

On latency, algorithm A takes 4 message delays for both reads and writes in every execution, and TEE-Rex takes 4 message delays in crash-free executions. These counts do not depend on nnn or on the thresholds. For comparison, the paper cites 4 and 8 message delays for writes and reads of Byzantine-resilient SWMR wait-free atomic registers. On storage, static registers need disks at at least 2k+r+12k + r + 12k+r+1 replicas when 2k+r+1≤n<2k+b+12k + r + 1 \le n < 2k + b + 12k+r+1≤n<2k+b+1 and none when n≥2k+b+1n \ge 2k + b + 1n≥2k+b+1; TEE-Rex uses none.

The bounds scale linearly in the failure parameters. In the static model each additional tolerated faulty replica costs two replicas, and each additional replica that may restart or roll back, whichever count is smaller, costs one more. In the dynamic model, each additional replica that may never stabilize and each additional replica that may crash at all costs one replica each.

Under adverse conditions, safety is unconditional: A2 is safe in any execution, including below its resilience bound, and TEE-Rex is safe in every CRR execution with any number of rollbacks. Liveness is conditional. Algorithm A is live only within its static thresholds. TEE-Rex is live when at least n−dn - dn−d replicas are eventually up and either crashes are more than MΔM\DeltaMΔ apart with M≥12M \ge 12M≥12 (M≥6M \ge 6M≥6 for the basic variant that assumes monotonic incarnation numbers), or at least n−cn - cn−c replicas never crash. TEE-Rex must know ddd but not ccc.

Several aspects are outside the paper’s scope. The object is a read/write register; consensus and state machine replication are discussed only through related work. The number of messages sent, the number of iterations of TEE-Rex’s validation loop under contention, and the cost of repeated crash-vector reads are not quantified. Recovery time is bounded only under the spacing condition, as at most 12Δ12\Delta12Δ for the enhanced protocol. The TEE is assumed to guarantee that replicas run their prescribed code; attacks other than rollback on the TEE itself are not modeled. No wall-clock performance, throughput, or comparison against SGX-based systems is reported.

My take

What I find strongest is the static characterization. The bound n≥2k+min⁡(b,r)+1n \ge 2k + \min(b, r) + 1n≥2k+min(b,r)+1 tells me exactly when rollbacks are as expensive as Byzantine faults and when they are not, and one partition argument explains both the resilience bound and the storage bound. The counterexamples against Guerraoui et al. and Dinis et al. are just as valuable to me: they show that the obvious recovery rule, copy the freshest state from a read quorum, is wrong, and that published protocols fell into it or a close variant.

My main doubt is that everything here is on paper. There is no implementation and no measurement. The 4-message-delay figure holds for crash-free executions, but TEE-Rex’s write loop can repeat rounds and issue extra crash-vector reads while replicas restart concurrently, and the paper does not bound how often that happens. I would want a prototype on real enclaves before believing the latency story under churn.

The dynamic model carries the TEE-Rex result, and that is where I would push hardest. Because TEE-Rex keeps all state in enclave memory, an event that restarts every replica together, such as a site-wide power loss, leaves no active replica to recover from. CRR-D excludes this by requiring either crashes spaced more than MΔM\DeltaMΔ apart or n−cn - cn−c replicas that never crash. With M≥12M \ge 12M≥12 and Δ\DeltaΔ a delay bound the processes cannot observe, I would test whether an attacker who controls power to some machines can time restarts inside that window. Safety would hold, since TEE-Rex is safe in every execution, but operations could stall, and whether a safe-but-stuck register is acceptable depends on the application.

There is also a real trade-off an operator has to make. Tolerating the static model through CRR-D needs 2k+b+12k + b + 12k+b+1 replicas instead of the optimal 2k+r+12k + r + 12k+r+1 when r<br < br<b. The paper presents the disk-based A1 and the disk-free TEE-Rex as separate points; I would like to see hybrids that use sealed storage where it is affordable and distributed recovery to catch the rollbacks.

The whole construction trusts the enclave to run the prescribed code. Side channels or enclave compromise are outside the model, and in that case a replica is Byzantine again; the paper does not say how the system degrades.

Finally, the TEE-Rex proofs rest on subtle minimal-counterexample arguments about durability and crash-consistency, in an area where earlier protocols turned out to be wrong. Model checking or a mechanized proof of TEE-Rex would raise my confidence considerably. And the register is a stepping stone: most TEE-based fault-tolerant systems run consensus or state machine replication, which is where rollbacks matter most and where this paper stops.
