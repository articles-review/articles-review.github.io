A BFT ordering service for Fabric, and the library under it

October 12, 2026
Tags: consensus bft blockchain fabric

Fabric’s ordering service receives endorsed transactions from clients and emits a stream of blocks. When we wrote this paper the latest release, v2.3, ran it on Raft, which tolerates crashes and nothing worse. The paper describes how my co-authors and I made Fabric Byzantine fault-tolerant end to end: a consensus library in Go, based on the BFT-SMaRt protocol, and the changes to the orderer, the peer and the client that had to come with it.

Why the 2018 attempt was not adopted

In 2018 Sousa et al. took the Kafka-based ordering service of Fabric v1.1 and replaced Kafka with a cluster of BFT-SMaRt servers. The proof of concept showed promising performance and was still not adopted by the community.

It was two processes in two languages, a Go front end and a Java BFT server. The code that wrapped the BFT-SMaRt core did not include Fabric’s membership service provider, so the cluster’s signatures were not compliant with Fabric’s and its identities were not part of Fabric’s configuration. Blocks carried the signature of a single front-end orderer, so nobody looking at a block could be convinced that a BFT service had produced it. And a follower could not validate the leader’s proposal against Fabric’s semantics without pulling in a significant amount of Fabric’s code.

Our candidates were BFT-SMaRt and PBFT, and we soon realized that rewriting the Java or C implementation in Go would not be enough.

Quorums, Raft against PBFT

Loosely speaking, a crash fault tolerant protocol like Raft needs a simple majority, and a Byzantine fault tolerant one like PBFT needs two thirds. With NNN nodes and a quorum of size QQQ:

QCFT=12NQBFT=23NF=N−Q Q_{\mathrm{CFT}} = \tfrac{1}{2}N \qquad Q_{\mathrm{BFT}} = \tfrac{2}{3}N \qquad F = N - Q QCFT​=21​NQBFT​=32​NF=N−Q

So the BFT cluster needs more replicas to survive the same number of faults FFF. In our evaluation, resilience to two faults takes 7 BFT nodes against 5 for Raft. PBFT also runs three communication rounds where Raft runs two, and it needs cryptography.

A library that calls back into Fabric

The library is embedded in the ordering node’s process, as the Raft library is. The difference is the interface. In the monolithic BFT-SMaRt cluster the flow starts with submit and ends with deliver. Ours adds functions that the application implements and the library calls while the protocol runs.

The leader batches incoming transactions and calls Assemble, and Fabric decides how the batch becomes a block. A configuration transaction, for instance, must sit in a block by itself. A follower that receives the proposal calls VerifyProposal, because the leader may be malicious. Fabric checks that the block is correctly numbered, that its header contains the hash of the previous block, and that every transaction in it is valid. In the commit phase each node calls SignProposal and sends the signature as part of its COMMIT message.

    Note over L,F: Deliver(block, Q signatures)

A node that receives a quorum of COMMIT messages delivers the block together with Q=2F+1Q = 2F+1Q=2F+1 signatures, and they are saved with it in the block store. Collecting the signatures during the commit phase keeps the protocol at three rounds, where the 2018 design needed four, and it lets an observer of a single block check that the ordering service agreed on it.

Clients submit to all nodes, not only to the leader. If a request is not included in a proposal after a first timeout, every non-faulty follower forwards it to the leader. After a second timeout they initiate a view change. The first step protects against a malicious client that sends only to followers to force a view change, the second against a faulty leader.

Peers and clients had to change too

Fabric’s default policy accepts a block with a single signature from a node of any organization in the ordering service consortium. We implemented a validation policy that requires signatures from QQQ out of NNN nodes of the consenter set defined in the last channel configuration transaction, and it is updated every time that set changes.

Blocks signed this way cannot be forged, but a peer that receives its blocks from a single orderer can still be censored. Asking F+1F+1F+1 orderers for the full stream would work and is expensive. Instead the peer requests full blocks from one randomly selected orderer and a stream of only headers and metadata from all the rest. If FFF or more of those streams are ahead of the full block stream for more than a threshold period, the peer suspects the orderer of censorship and replaces it. On the client side we modified the Fabric Java SDK to submit every transaction to all the orderers.

What it costs in throughput

We compared it with the Raft ordering service from Fabric v2.3, using transactions of about 4KB. With 1000 transactions per block and resilience to two faults, the BFT service did 2,500 tx/sec in a LAN against 13,000 for Raft, which is 20%. With the servers in ten data centers across the globe it did 1,200 against 3,000, which is 40%.

We attribute the gap mainly to two things: the cryptographic computations required in all BFT protocols, and the lack of pipelining in the BFT-SMaRt protocol. Our leader starts consensus on a block only after the previous one has been committed. We chose BFT-SMaRt for that simplicity. With a single proposal from a given leader at any point in time the view change sub-protocol is much simpler, and that increases our confidence in the correctness of the implementation. These numbers are for a single channel, and a Fabric network can scale horizontally by adding channels.

My take

If I had to keep one thing from this paper it would be the interface, not the protocol. Letting the application assemble, verify and sign the proposal while consensus runs is what made a BFT orderer fit into Fabric at all, and it would work just as well with a different protocol underneath.

We gave up pipelining on purpose. One proposal per leader at a time keeps the view change simple enough that I trust the implementation, and the price is plain in the numbers: 20% of Raft in a LAN, 40% in a WAN. I would make the same trade again for a first production-grade BFT orderer. I would not claim it is the right trade forever.

The comparison with Raft is honest about what it measures: 7 nodes against 5, 4KB transactions, a single channel. It says little about the workloads where most Fabric networks sit, well below either ceiling. For those the question is not how fast but what it costs to operate seven orderers across organizations.

The part I would want tested harder is the block delivery on the peer. Detecting censorship by comparing header streams against one full stream rests on a threshold period, and the paper does not say how to choose it or how the peer behaves when the network, not the orderer, is slow.

What the paper understates is how much of the effort was outside consensus. The signature policy on the peer, the delivery service and the SDK change are each small on the page, and without any one of them the system is not Byzantine fault-tolerant end to end.
